Gëstu ETP — Cycle de Vie d'une Mission d'Audit

Détail fonctionnel complet : statuts, workflows, artefacts, validations et livrables

Vue d'ensemble du cycle

Une mission d'audit suit 6 phases linéaires (audit standard) ou 5 phases (supervision continue). Les contrôles transversent ces phases de manière progressive jusqu'à clôture. Le système enregistre les évaluations (assessments) au niveau contrôle, puis génère des constats (findings), demandes correctives (CAR) et rapports.

Phases (standard):
initialization/scoping → planning → fieldwork → internal_review → client_review → closure

Source : src/features/missions/mission-constants.ts (MISSION_PHASES), src/types/database.types.ts (MissionStatus type)
Phase 1 : CADRAGE (Scoping)

Statut mission: scoping

Objectif: Fixer le périmètre, les objectifs, critères, parties prenantes, documents et acteurs de la mission.

Activités et artefacts

  • Défition des objectifs audit : mission.audit_objectives, audit_criteria, scoping_notes
  • Sélection du framework : lien vers une référentiel (ex. PSSAI, COBIT)
  • Import organigramme : chargement de la structure client via OrgChartImportModal
  • Questionnaire cadrage : lance un QuestionnaireInstance pour collecter contexte client
  • Gestion des contacts : création des ClientPortalContact pour accès au portail client
  • Demandes initiales de preuves : création des MissionEvidenceRequest optionnelles
  • Livrables générés : Note de cadrage PDF (optionnel)

Validations et transitions

  • Lead auditeur complète les champs obligatoires (objectives, criteria)
  • Questionnaire soumis par lead
  • Passage vers planning : manuel (clic lead) ou via étape guidée

Phase 2 : PLANIFICATION (Planning)

Statut mission: planning

Objectif: Affecter les contrôles aux auditeurs, définir calendrier, préparer ressources.

Activités et artefacts

  • Affectation des contrôles : création des MissionControlAssignment (contrôle → auditeur)
  • Définition des équipes : ajout des MissionMember (rôles: auditor, associate, lead_auditor)
  • Calendrier : dates de début/fin mission (mission.start_date, end_date)
  • Stratégie de preuve : choix des preuves obligatoires vs optionnelles par contrôle via MissionEvidenceOverride
  • Documents de référence : uploads initiaux pour contextualiser l'audit

Validations et transitions

  • Tous les contrôles du framework affectés à au moins un auditeur
  • Lead et associate identifiés
  • Passage vers fieldwork : transition lead auditeur

Phase 3 : TRAVAUX (Fieldwork)

Statut mission: fieldwork

Objectif: Auditeurs rédigent les évaluations de contrôles, collectent preuves, identifient constats.

Workflow d'évaluation de contrôle

Chaque contrôle assigné passe par un assessment avec le cycle de statuts :

Statut Assessment Rôle actif Actions
draft Auditeur assigné Rédige observations, preuves, notes. Pas visible aux autres. État initial.
submitted Auditeur Soumet pour revue interne. Visible au lead et associate.
in_review Lead/Associate En révision interne. Peut être rejeté ou approuvé.
approved Lead/Associate Validé. Prêt pour envoi au client (phase client_review).
rejected Auditeur (après rejet) Revenir à draft et corriger suite aux commentaires de révision.

Contenu d'une évaluation (ControlAssessment)

  • evidence_notes : notes sur les preuves collectées
  • observations : faits observés durant l'audit
  • conformity_level : évaluation conforme/partiellement/non-conforme/NA
    Conforme (C) Largement (LC) Partiellement (PC) Non-conforme (NC) N/A
  • findings : constats détaillés (table assessment_findings, N findings par assessment)

Modèle Constats (AssessmentFinding) — NEW

Chaque assessment peut contenir plusieurs constats indépendants, chacun avec:

  • classification : major_nc | minor_nc | observation | strength
  • description : texte du constat
  • risk : analyse de risque associée
  • recommendation : recommandation auditeur
  • priority : critical | high | medium | low
  • proposed_deadline : délai proposé pour correction
  • ai_generated : flag pour suggestion IA

Source: assessment_findings table, visible en phase revue/client_review/clôture

Gestion des preuves (Evidence Requests)

Cycle d'une demande de preuve

pending : demande créée, en attente client
uploaded : client a téléchargé preuve, auditeur à valider
accepted : preuve validée par auditeur
declined_by_client : client déclare preuve inexistante/non-applicable/confidentielle
reissued : auditeur réémet demande après rejet client
escalated_to_finding : absence preuve devient un constat (major_nc/observation)

Source : MissionEvidenceRequest table + useMissionEvidenceRequests.ts

Interface et UX

  • ControlWorkArea : édition assessment, étapes guidées (observer → documenter → analyser → validation)
  • RightRail : preuves, commentaires, observations équipe
  • Shortcuts : clavier pour naviguer (J/K pour contrôle suivant/précédent, etc.)

Phase 4 : REVUE INTERNE (Internal Review)

Statut mission: internal_review

Objectif: Lead et associate valident/rejettent les assessments soumis, assurent cohérence et qualité.

Workflow de validation interne

Étape Rôle Actions
auditor_submitted Auditeur Assessment passé de draft → submitted
lead_review Lead auditeur Revue, approbation ou rejet avec commentaires
associate_review Associate (optionnel) Revue complémentaire si configuré
Validation finale Lead Assessment → approved ou rejected (retour auditeur)

Données de révision (AssessmentValidation)

  • Enregistre chaque étape (stage), décision (approved/rejected), commentaires
  • Piste d'audit complète (qui a validé, quand)
  • Permet rejets multiples → corrections → nouvelles soumissions

Artefacts produits

  • Synthèse des constats : agrégation par classification (NC maj/min, observations)
  • Score de conformité : moyenne pondérée (c=100, lc=75, pc=50, nc=0, NA exclu)
  • Plan d'action préliminaire : génération auto des CAR à partir des NC majeures/mineures

Phase 5 : VALIDATION CLIENT (Client Review)

Statut mission: client_review

Objectif: Client valide assessments approuvés, pose observations non-bloquantes, lance portail de suivi d'actions.

Accès portail client

  • Contacts portail : ClientPortalContact avec statut (pending/invited/active)
  • Permissions : ClientPermission (contributor | viewer | approver)
  • Missions accessibles : ClientMissionAccess régit qui voit quoi

Revue de contrôles côté client

Client accède via portail à chaque approved assessment :

  • Vue des contrôles, conformité, constats et recommandations
  • Permissions : approver peut valider/rejeter, viewer lit seul
  • Decision : approved → constat accepté, rejected → contestation client
  • Observations : client poste observations non-bloquantes (table AssessmentObservation)

Observations client

Flux d'observation-réponse:

  • observation_text : client pose question/doute
  • observation_by/at : auditeur/lead réagit
  • response_text : réponse auditeur
  • response_action : modified (constat modifié) | kept (constat maintenu)

Observations non-bloquantes, le contrôle reste approuvé

Interface

  • ClientMissionDetailPage : vue client du détail mission
  • ControlDetailDrawer : évaluation détaillée + revue
  • ClientReviewPanel : validation et commentaires
  • SmartInterviewContainer : questionnaires client + demandes de preuves

Phase 6 : CLÔTURE (Closure)

Statut mission: closure

Objectif: Finaliser audit, générer rapports, consolider plan d'action client.

Synthèse de conformité

  • Score global : moyenne pondérée sur tous les approved assessments
  • Répartition domaines : score par domaine (ex. domaine A.5: 75%)
  • Histogramme conformité : nb contrôles C/LC/PC/NC/NA
  • Conclusion audit : conformant | partially_conformant | non_conformant

Constats agrégés (Finding Synthesis)

  • Tous les assessment_findings des assessments approved, triés par sévérité
  • Agrégation : NC maj | NC min | Observation | Strength
  • Support pour synthèse narrative et graphique

Livrables PDF/PPTX/Excel générés

Rapport d'Audit (PDF)

  • En-tête avec logo/adresse cabinet
  • Distribution client (RSSI + contacts)
  • Contexte audit (objectifs, périmètre, cadrage)
  • Synthèse conformité + score domaines
  • Constats détaillés par domaine
  • Recommandations par constat
  • Annexes (questionnaires, documents)

Source: src/features/reports/generateAuditReportPDF.ts + audit-report/ modules

Plan d'Action (Excel)

  • Toutes CAR (Corrective Action Requests)
  • Classification (NC maj/min, obs)
  • Recommandations auditeur
  • Responsable client + deadline
  • Statut CAR (open/responded/verified/closed)
  • Suivi vérification auditeur
  • Graphiques de progression

Source: src/features/reports/generateActionPlanXLSX.ts

Note de Cadrage (PDF)

Plan d'Action Correctif (CAR Management)

  • Création auto : à partir NC majeures/mineures (classifications major_nc, minor_nc)
  • Status CAR : open → client_responded → verified → closed
  • Vérification : auditeur valide réponse client (pending/accepted/rejected)
  • Suivi : en phase action_plan (post-clôture), client répond aux actions, auditeur vérifie

  • DomainBreakdownList : détail domaines
  • FindingSynthesis : agrégation constats par classification
  • ReportGenerator : boutons génération PDF/Excel/PPTX

Phase Virtuelle : PLAN D'ACTION (Action Plan)

Contexte: Visible uniquement en phase closure, gestion des corrections post-audit

Cycle de vie CAR

Statut CAR Étape de vérification Rôle actif Actions
open pending Client Client planifie et engage action corrective
client_responded pending Auditeur Client a fourni réponse/preuve, auditeur à valider
client_responded accepted Auditeur Preuve acceptée, CAR → verified
client_responded rejected Auditeur Preuve rejetée, client doit re-soumettre
verified - Lead CAR → closed après validation complète
closed - - Action corrective terminée et clôturée

Vue & gestion

  • Deux modes : List (tableau) ou Timeline (calendrier)
  • Filtres : par status, classification, recherche texte
  • ActionPlanKPIs : nb CAR ouvertes, répondues, vérifiées, clôturées
  • Liens bidirectionnels : CAR ← assessment_findings (source de vérité)

Surveillance Continue (Optionnel)

Kind = continuous_supervision : modèle de missions répétées et cycliques.

  • SupervisionCycle : périodes d'audit (ex. T1, T2, T3, T4)
  • Phases adaptées : scoping → planning → fieldwork → internal_review → closure (pas client_review)
  • Assessments cyclés : chaque assessment lié à cycle_id
  • Évaluation dynamique : comparaison écart d'un trimestre à l'autre

Implémentée mais moins utilisée que audit standard. Voir useMissionProgress.ts pour logique phases.

Validations & Gestion des Statuts

Règles de progression

Critères de passage de phase: Le système n'applique pas de blocage automatique strict, mais expose des nextAction au lead auditeur via useMissionProgress :
  • scoping→planning : questionnaire cadrage soumis
  • planning→fieldwork : équipe et affectations complètes
  • fieldwork→internal_review : tous contrôles soumis (status ≠ draft)
  • internal_review→client_review : tous assessments approved
  • client_review→closure : client validation complète

Calcul des KPIs

  • overallPercent : 50% phase avancement + 50% assessments soumis/approuvés
  • conformityScore : moyenne pondérée c=100, lc=75, pc=50, nc=0 (NA exclu)
  • daysRemaining : delta date fin mission
  • assessedControls : count status ∈ {submitted, in_review, approved}
Source: src/features/missions/useMissionProgress.ts (définit MissionProgress interface et logique complète)

Sécurité & Row-Level Security (RLS)

  • Missions : auditeurs ne voient que missions cabinet courant + rôle spécifique
  • Assessments : auditeur voit seulement ses assessments (sauf lead/associate)
  • Client Review : client ne voit que ses missions + assessments approuvés
  • Admin : service_role bypass RLS pour opérations critiques (création mission, transitions de phase)
Conventions: voir CLAUDE.md § Sécurité : jamais RLS auto-référente, utiliser SECURITY DEFINER functions (get_my_user_id(), get_my_organization_id(), etc.)

Points Clés d'Architecture

Séparation responsabilités

  • Hooks : useMissionDetail, useReviewAssessments, useClientMissionDetail — chargement données
  • Tabs : MissionScopingTab, MissionFieldworkTab, etc. — vue d'ensemble phase
  • Composants : sections, cards, modals — logique métier encapsulée
  • Reports : génération PDF/Excel hors UI (Web Workers pour PDF)

État et localStorage

  • Préférence vue Fieldwork (right-rail open/close) : localStorage:gestu:fieldwork-right-rail-open
  • Préférence vue Missions : liste/kanban/cards sauvegardée
  • Aucune donnée critique en localStorage (mutations via API)

Gestion asynchrone

  • Tous les useEffect async munis d'AbortController
  • Mutations via Supabase functions serverless (client-review-assessment, request-evidence, etc.)
  • Gestion d'erreurs : log console + toast utilisateur (messages génériques)

Livrables & Exports

Par phase

  • Scoping : Note de cadrage PDF (optionnel)
  • Planning : Planning projet, affectations
  • Fieldwork : Observations preuves, constats draft
  • Internal Review : Constats finalisés, score conformité
  • Client Review : Validation client, observations
  • Closure : Rapport audit PDF (principal), Plan action XLS, Compte-rendu entretiens PDF
  • Action Plan : Suivi CAR, état validations
