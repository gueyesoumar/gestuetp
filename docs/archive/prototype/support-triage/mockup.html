Reformulation

Ajouter un bouton « Exporter en Excel » sur l'onglet Plan d'action (portail client + côté auditeur) générant un .xlsx des actions correctives de la mission.

Déjà présent ? ✓ RÉUTILISABLE

Partiellement : génération de rapports PDF déjà en place (générateurs lazy-loaded), et la lib xlsx est déjà au projet (Edge Functions smart-*). Aucun export Excel du plan d'action aujourd'hui → pas de doublon.

Fonctionnel ✓ CLAIR

Colonnes : contrôle · constat · action · responsable · échéance · statut. Rôles : client & auditeur. Cas limites : plan vide, gros volumes.

Impact technique ✓ LIMITÉ

UI: ClientActionPlanTab · hook: useClientActionPlan (données déjà chargées) · table: corrective_action_requests (lecture) · migration: aucune · Edge Function: aucune si export client

🔒 Sécurité ✓ FAIBLE RISQUE

Lecture seule de données déjà visibles par l'utilisateur ; la RLS de corrective_action_requests s'applique déjà. Export généré côté client → aucune nouvelle surface. ⚠️ Si export déplacé côté serveur plus tard : cloisonner par cabinet.

🛡️ Conformité / RGPD ⚠️ POINT D'ATTENTION

Le plan d'action contient des noms de responsables (données personnelles). L'export est une sortie locale vers un utilisateur qui y a déjà accès → pas de nouveau traitement ni transfert tiers. Recommandé : journaliser les exports (qui / quoi / quand) pour la piste d'audit — cohérent avec un produit de conformité.

Complexité / effort ✓ TAILLE S

Effort estimé 0,5–1 j-h. Confiance de l'analyse : 85% (élevée) — lib et données déjà présentes, périmètre clair. Pas de migration.

Hypothèses & questions ouvertes

  • Hypothèse : export généré côté client à partir des données déjà chargées (pas d'Edge Function).
  • Question : faut-il tracer les exports dans un journal d'audit ? (impacte le point RGPD ci-dessus)
  • À confirmer : comportement attendu si > 1000 lignes (pagination ou génération serveur).
